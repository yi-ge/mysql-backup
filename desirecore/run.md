# MySQL Backup in DesireCore

Run the backup worker as an independent, always-on deployment. It owns MySQL credentials, the schedule, archives, member accounts, and the operation database. A DesireCore installation serves the same React workbench as a console and forwards its scoped business requests to that worker. Closing either host UI leaves scheduled work running.

## Prepare and install

1. Build/publish the Docker image from the recorded source commit to a registry you control, then generate these materials using its immutable registry digest. Make the exact image available on the Docker daemon connected to the target DesireCore service.
2. Prepare this material directory in DesireCore Application Authoring. Request Docker runtime preparation for the returned application instance using container port `80`, an available host loopback port, identity path `/.app-identity` and the chosen startup policy. Execute the command supplied by DesireCore through its accepted execution tool, complete enrollment using its actual terminal receipt, then commit the installation. Stop the candidate through its owner before first opening the committed installation.
3. In the registered **formal installation data root**, write a file named `console.json` containing `{"upstream":"https://backup.example.com"}`. Use the worker's trusted HTTPS origin. Keep this file out of the release. Restart the console runtime after changing it. Desktop and Web installations can point their individual data roots to the same worker.
4. Open **My Apps → MySQL Backup** and sign in with a worker account. For initial setup, obtain the one-time code from the worker's own data volume. Workers serving a managed console must define `MYSQL_BACKUP_PUBLIC_URL` for archive download links.

The app honors the injected `PORT`, `APP_DATA_DIR`/`APP_DATA_ROOT` and Docker runtime proof variables. Its identity route is for the runtime owner. In Desktop, the workbench receives the standard application SDK. A remote Web deployment must enable DesireCore's separate HTTPS app host with a wildcard DNS/certificate and trusted shell origin. Set `allowedMethods` to `['GET', 'HEAD', 'POST']` and `allowedPathPrefixes` to `['/']` in the app Web Host policy. Set `MYSQL_BACKUP_PUBLIC_URL` to the operator-accessible worker HTTPS origin. An operator copies a short-lived, one-use download link from the embedded workbench and opens it in their browser. This also keeps archive bytes out of the Web gateway. Session credentials are exchanged within the workbench protocol. The gateway does not forward platform credentials.

The optional **Investigate with Agent** action requires the installation's explicit `requestWork` grant and an assigned agent with the MySQL Backup MCP service configured. The action opens a proposed assignment through the host. It uses plan and run IDs and leaves worker credentials with the worker. Register the Streamable HTTP endpoint `https://backup.example.com/mcp` in DesireCore's MCP service settings. Add the worker-issued token to the server header `Authorization: Bearer TOKEN`. Use read scope for investigations. A worker admin can issue an operate token when the intended agent also needs backup, thaw, or recovery operations. Configure DesireCore approval for those tools if applicable.

The managed console is replaceable. Keep the worker volume and its private key independently backed up. Reinstalling the console does not migrate worker data. For a standalone Worker, upgrades, recovery and rollback, see the source repository README.
